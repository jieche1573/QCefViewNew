# 流程图存储方案设计

## 一、需求分析

### 1.1 数据结构

当前流程图包含以下信息：

- **流程基本信息**：流程名称、实施节点、等级
- **节点信息**：
  - 开始/结束节点（start/end）
  - 有人节点（person）：关联岗位ID
  - 有人有车节点（personCar）：关联岗位ID + 设备ID
- **边信息**：节点之间的连接关系
- **布局信息**：节点坐标、缩放比例等

### 1.2 业务需求

1. 保存和加载流程图设计
2. 流程图导出为JSON供仿真系统使用
3. 统计分析：
   - 某个岗位在哪些流程中使用
   - 某个设备在哪些流程中使用
   - 某个机型有哪些流程
4. 数据一致性：岗位、设备名称修改后自动同步

## 二、方案对比

### 方案1：纯JSON存储（简单方案）

#### 2.1.1 表结构

```sql
CREATE TABLE process_flow (
    id VARCHAR(50) PRIMARY KEY,
    model_id VARCHAR(50) NOT NULL,           -- 机型ID
    name VARCHAR(100) NOT NULL,              -- 流程名称
    implement_node VARCHAR(50),              -- 实施节点
    level VARCHAR(20),                       -- 等级
    graph_data TEXT,                         -- JSON格式的完整流程图数据
    create_time DATETIME,
    update_time DATETIME,
    FOREIGN KEY (model_id) REFERENCES model(id)
);
```

#### 2.1.2 graph_data JSON示例

#### 2.1.3 优点

✅ **实现简单**：一张表搞定，前端直接存取JSON
✅ **加载快速**：一次查询获取完整数据
✅ **版本控制**：易于备份和恢复
✅ **前端友好**：数据格式与前端一致，无需转换

#### 2.1.4 缺点

❌ **数据冗余**：存储了personName、carName等冗余信息
❌ **查询困难**：无法直接查询"哪些流程用了某个岗位"
❌ **数据不一致**：岗位名称修改后，JSON中的名称不会自动更新
❌ **统计分析难**：需要解析JSON才能统计
